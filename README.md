# Кандидатогенерация для поиска услуг Авито

Задача: по поисковому запросу отобрать из корпуса 189 тысяч объявлений до 50 кандидатов так, чтобы в них попали объявления, которые пользователь в итоге выбрал. Метрика Recall@50.

Итоговая схема простая: для каждого запроса по всему корпусу считаю несколько сигналов, из трех комбинаций сигналов беру топы и объединяю, дальше LightGBM ранжирует объединение и оставляет 50.

## Результаты на валидации

| что | Recall@50 |
|---|---|
| BM25 по заголовку, параметрам и описанию | 0.438 |
| BM25 только по локациям, куда ходят из локации поиска | 0.638 |
| источник lex: BM25 + приор рубрики + приор локации | 0.904 |
| источник dense: дообученный энкодер + те же приоры | 0.919 |
| источник profile: похожесть на то, что выбирали по похожим запросам | 0.843 |
| объединение трех источников (~464 кандидата) | 0.989 (потолок) |
| ранкер поверх объединения, обучен на rank | 0.960 |
| **ранкер + запросы extra + признаки покрытия слов** | **0.963** |

На лидерборде первая версия ранкера (0.960 на val) получила 0.924. Разбор этого расхождения ниже в разделе про ошибки.

Разбивка итогового ранкера по частям валидации:

| часть val | запросов | Recall@50 |
|---|---|---|
| текст запроса встречался в base | 1093 | 0.971 |
| новый текст | 1907 | 0.959 |
| позитив лежит в самом корпусе бенчмарка | 190 | 0.942 |

Разрыв между позитивами с историей и без нее около одного пункта, значит модель не держится на запоминании конкретных объявлений.

## Данные и валидация

В train 497 тысяч пар запрос и выбранное объявление. Я сгруппировал их в поиски: поиск это уникальный набор признаков запроса (текст, локация, фильтры, категория), все выбранные в нем объявления считаются позитивами.

Посмотрел, чем бенчмарк отличается от train:

- в бенчмарке 2452 запроса и все тексты уникальные;
- 37% текстов бенчмарка встречаются в train;
- если взять по одному случайному поиску на случайный уникальный текст из train, то у 37.4% таких текстов в train остаются другие поиски с тем же текстом.

Отсюда способ собрать валидацию, похожую на бенчмарк. Беру 3000 случайных текстов и по одному поиску на каждый, это val. Еще 24000 текстов так же откладываю для обучения ранкера (rank). Поиски, где выбранные объявления уже лежат в корпусе бенчмарка, идут в extra, это тоже данные для ранкера. Все остальное (base) идет на статистики и дообучение энкодера.

Для отложенного запроса корпус собирается так же, как в бенчмарке: весь benchmark_items плюс позитивы отложенных запросов. rank нарезан на фолды по 3000 запросов, и каждый запрос видит только позитивы своего фолда. Так в корпус подмешано примерно столько же чужих позитивов, сколько их в самом бенчмарке.

Проверил, что валидация не проще бенчмарка:
- размер пула объявлений в точной локации поиска у val и у бенчмарка сопоставим (медиана около 1000 и 1600);
- вокруг позитива примерно столько же объявлений той же локации и подкатегории (медиана 13 и 12).

## Ошибки и что с ними сделал

**Утечка через историю объявления.** Первая версия статистик давала на валидации подозрительно хорошие цифры. Оказалось, 37% позитивов валидации уже выбирали в base по другим запросам, а у объявлений бенчмарка история есть только у 9%. Любой сигнал вида «это объявление раньше выбирали» на валидации работает сильно лучше, чем будет на бенчмарке. Поэтому все статистики из base (переходы между локациями, рубрики похожих запросов, профили заголовков) и пары для дообучения энкодера строятся без объявлений, которые есть в корпусе. Популярность конкретных объявлений я не использую вообще.

**Жесткий фильтр по локации.** Если искать только в локациях, куда ходили из локации поиска, пул в медиане 62 тысячи объявлений, и BM25 внутри него дает 0.638. Если вместо фильтра добавить к скору мягкий приор `1.5 * log P(локация объявления | локация поиска) + [та же локация] - log(1 + расстояние в км)`, получается 0.90. Это самый сильный рычаг во всем решении.

**Регионы.** Часть поисков идет по региону, например по Московской области, а объявления привязаны к городам. Такие локации поиска не имеют своих объявлений, их центр я считаю по объявлениям, которые из них выбирали.

**Фильтры поиска.** Фильтр «Вид услуги X» находится в параметрах 97% выбранных объявлений, «Тип услуги Y» в 94%. Как жесткий фильтр это теряет несколько процентов позитивов, поэтому фильтр идет в запрос BM25 с весом 0.5 и отдельным признаком в ранкер. Фильтры вроде «Кто оказывает услуги» или «Срочная услуга» в параметрах объявления не отражаются, их не использую.

**Ранкер.** Первый ранкер обучался на прореженных негативах и проиграл лучшему одиночному источнику. После перехода на всех кандидатов и lambdarank он стал заметно лучше.

**Валидация оптимистичнее лидерборда.** Первая отправка дала 0.924 при 0.960 на val. Что проверил:

- Корпус бенчмарка гуще вокруг запросов бенчмарка. Кандидатов в той же локации и самой вероятной подкатегории у запроса бенчмарка в медиане 29, у запроса val 7. Объявления корпуса в два раза чаще имеют рядом похожий запрос бенчмарка, чем случайные объявления из train. Похоже, корпус собран вокруг выдачи по этим запросам. Перевзвешивание val под плотность бенчмарка объясняет только несколько десятых.
- Позитивы val в основном объявления из train, подмешанные в корпус. У тех 190 запросов val, где позитив сам лежит в корпусе бенчмарка, recall был 0.926, почти как на лидерборде. На 1630 таких запросах из rank разницы почти нет, так что частично это шум маленькой выборки.
- Если подмешать к запросу val объявления, которые в base выбирали по похожим запросам в той же локации (псевдо выдача), recall падает с 0.960 до 0.948.
- Снимок объявлений один: у 18 тысяч общих объявлений train и корпуса совпадают отзывы, цены и тексты. Сдвига по объявлениям нет.
- В бенчмарке 9% поисков без категории (search_category = 0), в train их практически нет. В корпусе есть 1876 объявлений не из услуг. Для 25% поисков без категории самое похожее объявление корпуса как раз не из услуг, а для обычных поисков и для val таких меньше 1%. То есть корпус содержит объявления других категорий, подобранные именно под поиски без категории.

Что сделал. Нашлось 16.6 тысячи поисков из base, где выбранные объявления уже лежат в корпусе бенчмарка. Их история и так исключена из статистик, так что для base они бесполезны. Зато для ранкера это честные запросы с настоящим корпусом бенчмарка вокруг позитива. Они стали отдельной частью extra, и ранкер учится на rank + extra. Плюс признаки доли слов запроса в заголовке и в тексте объявления, потому что точные совпадения иногда проигрывали приорам. Все три проверки подросли: обычная val 0.960 → 0.963, запросы с позитивом из корпуса 0.926 → 0.942, val с псевдо выдачей 0.948 → 0.949. На лидерборде 0.924 → 0.930.

Пробовал для поисков без категории отдельный источник кандидатов не из услуг (энкодер и приор локации без приора рубрики) и отдавать ему 10 мест из 50. На лидерборде стало хуже: 0.930 → 0.928. Видимо объявления других категорий в корпусе это соседи по выдаче, а не то, что выбирали. Правило убрал.

## Сигналы

Все считается сразу для пачки запросов по всему корпусу, потом маскируется видимостью объявлений для фолда.

- **text.** BM25 (k1=1.2, b=0.75) по леммам pymorphy3. Документ: заголовок пять раз, параметры, полное описание. Обрезать описание плохо, минус 4-7 пунктов. Запрос: леммы текста с весом 1 плюс леммы фильтров с весом 0.5.
- **dense.** Энкодер deepvk/USER2-base, дообученный одну эпоху на парах из base (CachedMNRL, батч 512). Запрос: текст плюс фильтры. Объявление: заголовок, смысловые параметры и первые 300 символов описания. Из zero-shot моделей (e5 base и large, bge-m3, FRIDA, Qwen3-Embedding-0.6B, rubert-tiny2) USER2-base был лучшим.
- **mc.** Логарифм вероятности подкатегории объявления для запроса. Распределение складывается из рубрик 100 ближайших по символьным n-граммам текстов base, рубрик топ-200 объявлений по BM25 и множителя от фильтров поиска. Правильная подкатегория оказывается первой в 75% случаев и в тройке в 92%.
- **loc.** Приор локации из переходов base и расстояния до центра локации поиска.
- **profile.** Для запроса берем 50 ближайших текстов base, смотрим, какие объявления там выбирали, и строим TF-IDF профиль их заголовков. Сигнал это косинус профиля с заголовком объявления.

## Источники кандидатов

- lex = text + mc + loc, топ 300
- dense = 50 * dense + mc + loc, топ 200
- profile = 20 * profile + mc + loc, топ 200

Веса подобраны на валидации по небольшой сетке.

## Ранкер

LightGBM lambdarank на запросах rank и extra. Признаки:
- все сигналы, отставание от лучшего объявления запроса, места в каждом источнике;
- доля слов запроса в заголовке и во всем тексте объявления;
- вероятность и место подкатегории;
- доля совпавших фильтров;
- признаки объявления: отзывы, рейтинг, цена, длина описания, скрытый телефон;
- признаки запроса: длина, число фильтров, насколько близкий текст есть в base, региональный ли поиск.

## Как запустить

```
pip install -r requirements.txt
# положить train.parquet benchmark_items.parquet benchmark_queries.parquet в data/
./run_all.sh
```

Для точного воспроизведения отправленного файла сохранены дообученный энкодер и готовые эмбеддинги. Они не входят в репозиторий из-за размера. В архиве `avito_candgen_weights.zip` лежит папка `avito_candgen/work`, ее нужно перенести в корень репозитория под именем `work`. После этого шаг 2 пропустится, а полный прогон на CPU займет около полутора часов.

Без сохраненных файлов код обучит энкодер заново. На L4 это занимает около 40 минут. Кодирование готовой моделью занимает около 5 минут. Из-за вычислений в bf16 разные видеокарты могут дать небольшие отличия в итоговом порядке кандидатов.

Шаги по отдельности:

1. `prepare.py` собирает поиски, делит train на base, rank, val и extra, лемматизирует объявления.
2. `train_dense.py` дообучает энкодер и считает эмбеддинги.
3. `build_candidates.py` считает сигналы, кандидатов и признаки.
4. `train_ranker.py` обучает ранкер и печатает метрики на val.
5. `predict.py` пишет answer.csv и проверяет формат.

Все случайности зафиксированы через seed 42, LightGBM работает в детерминированном режиме.

## Что использовал

- pymorphy3 для лемматизации
- scikit-learn для TF-IDF
- sentence-transformers и модель deepvk/USER2-base с Hugging Face
- LightGBM для ранкера

Внешних API нет, все считается локально.
